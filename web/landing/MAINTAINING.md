# Maintaining the Fluvie landing site

This is the marketing landing at https://fluvie.dev. The page is
`web/landing/index.html`, plus the gallery clips under `web/landing/media/`. The
two data-driven regions, the package list and the lesson gallery, are generated
from `web/landing/landing_data.json` by `melos run web:landing` (a deterministic
script, no LLM); everything else is hand-edited static HTML.
`melos run web:landing:check` (run in CI and the gate) fails if the page drifts
from the data, or if a published package or a lesson has no entry.

This doc tells you exactly what to touch when the project changes. The docs site
(docs.fluvie.dev, Astro) and the demo (demo.fluvie.dev, Flutter web) are separate.
Do not edit them from here.

> The package list and gallery are data-driven: edit
> `web/landing/landing_data.json` and run `melos run web:landing`. For copy, new
> sections, links, or accessibility, the `sync-website` skill
> (`.claude/skills/sync-website/SKILL.md`) walks the editorial reconcile. This doc
> is the manual reference behind both.

## What lives where

- `web/landing/index.html` is the whole page (inline CSS). Hand-edited, except the
  package list and the lesson gallery, which `melos run web:landing` generates
  between the `region:packages` / `#region:gallery` markers.
- `web/landing/landing_data.json` is the data for those generated regions: the
  package list and the lesson gallery. Edit it, then run `melos run web:landing`.
- `web/landing/website-structure.md` is the design brief: structure, sections,
  motion, microinteractions, hover and focus, and accessibility. It defines intent.
  `index.html` is the implementation of it. It carries no colors or fonts (the
  design tool owns the brand CI). Keep them in sync: a structural change to the page
  should be reflected in the brief, and the other way around.
- `web/landing/media/` holds the per-lesson gallery clips:
  `<key>.mp4`, `<key>.webm`, `<key>.poster.webp`, and `<key>.gif`. Generated and
  committed. The `.gitkeep` keeps the directory tracked so the Docker build can copy
  it even before the first clip exists.
- `tool/web/regenerate_gallery.sh` is the gallery encoder (also `melos run
  web:gallery`).
- `documentation/fluvie_logo.svg` is the logo, copied in by the Dockerfile (not
  duplicated under `web/landing`).
- `deploy/landing.Dockerfile` packages the page, the media, and the logo into nginx.

## How the gallery is built

The reel-wall tiles are generated by the inline `<script>` at the bottom of
`index.html` from a `GAL` array (one row per lesson: `["NN", "Title", "what it
teaches", "category", isRealClip]`). Each tile shows an animated gradient poster;
lessons flagged `true` get a "LIVE CLIP" badge, the rest get a "play in demo"
affordance. The tiles link to `https://demo.fluvie.dev/#NN`. No video files are
required for the page to look complete.

The `tool/web/regenerate_gallery.sh` pipeline (and `web/landing/media/`) is an
**optional upgrade**: it renders real looping clips so a tile can embed actual
footage instead of a gradient poster. Wire it in only when you want real clips
(see "Optional: embed real clips" below).

## When a new lesson or example is added

A new `example/lib/lessons/NN_*.dart` means a new gallery tile.

1. Add a `lessons` entry to `web/landing/landing_data.json`: `key` (NN), `title`, a
   one-sentence `teaches` line, a `category` (`basics`/`data`/`media`/`audio`/
   `code`/`transitions`), and `clip` `false` (or `true` once it has a real clip).
   Keep the wording aligned with `website-structure.md`.
2. Run `melos run web:landing` to regenerate the gallery. `web:landing:check` fails
   until every lesson on disk has an entry.
3. If the category is new, add a matching `<button class="filterBtn" ...>` to the
   filter row (the filter row is static HTML).
4. Reload the page and check the tile appears, the filter includes it, and the
   `aria-label` describes the lesson.

### Optional: embed real clips

1. Register the key in `pubspec.yaml` under `render:examples` and in the `KEYS`
   array of `tool/web/regenerate_gallery.sh`.
2. Run `melos run web:gallery` (Flutter + ffmpeg) to render `build/<key>.mp4` with
   Impeller and encode `web/landing/media/<key>.{mp4,webm,poster.webp,gif}`. To
   re-encode only, run `tool/web/regenerate_gallery.sh --encode-only`.
3. In the gallery builder, swap that tile's gradient-poster `<div>` for the
   progressive `<video>`(webm, mp4) → `<img>` GIF fallback that points at
   `media/<key>.*`, and mark the lesson `true` in `GAL`.
4. Eyeball the clip: clean loop, under the size budget, captioned. Commit the media
   and the HTML together (see the determinism note below).

## When a package changes

The package list is generated from `web/landing/landing_data.json`, so it always
reflects the published `packages/*` (currently eight, including
`fluvie_mobile_encoder` and `fluvie_web_encoder`).

- New package: add a `packages` entry (`key`, `role`, a one-line `line`, an `icon`
  HTML entity, and `primary`/`badge` only for `fluvie`), then run
  `melos run web:landing`. `web:landing:check` fails until every published
  `packages/*` has an entry.
- Renamed or removed package: update or drop its entry and regenerate.
- Keep the brief's ecosystem list (`website-structure.md`) in step with the data.

## When copy or links change

- Tagline, hero, feature copy: edit in place. Obey the voice rules. Short sentences,
  second person, no em-dashes, none of the banned words (seamless, robust, leverage,
  powerful as filler, effortless, blazing, unleash).
- Canonical links to keep working: docs.fluvie.dev and its deep-links
  (getting-started/installation, getting-started/your-first-video,
  getting-started/core-concepts, guides/ai-and-mcp, guides/rendering-on-a-server,
  reference/cheatsheet), demo.fluvie.dev, mcp.fluvie.dev, the GitHub repo, and each
  pub.dev package page.
- After any link edit, do a quick dead-link pass. The page is small, so a manual scan
  or a one-shot link checker is enough.

## How to regenerate the gallery clips

- Re-render the source only when the lesson code changed: `melos run web:gallery`
  (Flutter plus ffmpeg). For a single key, render it directly with the CLI:
  `dart run packages/fluvie_cli/bin/fluvie.dart render <key> --out build/<key>.mp4
  --enable-impeller`.
- Re-encode the web assets any time (fast, ffmpeg only):
  `tool/web/regenerate_gallery.sh --encode-only`.
- Impeller is on by default in the script (it passes `--enable-impeller` to the CLI,
  which forwards it to `flutter test`). If the Impeller pass fails on a headless box
  with no GPU, the script retries that key with the default backend. To force the
  default backend, pass `--no-impeller`.
- The encoder writes a 480px-wide, muted MP4 with faststart, a VP9 WebM, a
  `poster.webp` first frame, and a two-pass palettegen and paletteuse GIF fallback.
  Change the width, fps, or quality knobs at the top of the script, not per tile.
- Determinism note: Fluvie frames are byte-identical, but ffmpeg builds differ across
  machines, so the encoded bytes can differ machine to machine. Regenerate all
  affected assets on one machine in one go, review them, and commit them together so
  the diff is coherent.
- If a render stalls at 0% CPU, the frame cache may have filled `/tmp`. Clear
  `/tmp/fluvie_*` and re-run.

## How the design brief relates

- `website-structure.md` is the source of truth for structure, hierarchy, sections,
  motion, microinteractions, hover and focus states, and accessibility. It contains
  no colors or font names (the design tool holds the brand CI).
- `index.html` is the implementation. When you change one, reconcile the other in the
  same PR. If you add a section to the page, describe it in the brief. If the brief
  calls for a new section, build it.
- Accessibility is non-negotiable in both: keyboard reachable, visible focus, good
  contrast, `prefers-reduced-motion` respected, every clip captioned via `aria-label`
  and `alt`, and no motion that hurts usability.

## How to deploy

- Local preview of the exact production artifact:
  `docker compose -f deploy/docker-compose.yml up --build fluvie-web`, then open
  http://localhost:8082 (the `fluvie-web` service, nginx:alpine).
- The image is `deploy/landing.Dockerfile`, with the build context at the repo root.
  It copies `web/landing/index.html`, `web/landing/media/`, and
  `documentation/fluvie_logo.svg`. If you add another top-level asset to the page, add
  a matching `COPY` line.
- Production (fluvie.dev) is GitHub Pages, served from the `SimonErich/fluvie_website`
  repo. Its `Deploy fluvie.dev` workflow pulls `web/landing` from this monorepo
  (index.html, the logos, og.png) and publishes it, so editing the page here is the
  whole job. The deploy runs on demand, daily, and on a `landing-changed`
  repository_dispatch (this monorepo's `notify-website` workflow sends it when
  `web/landing/**` changes, once a `FLUVIE_WEBSITE_TOKEN` secret is set).
- The Docker artifact (`deploy/landing.Dockerfile`, the `fluvie-web` compose
  service) is now just for local preview, not production.

## Release checklist

Run before shipping a landing change:

- [ ] Voice pass: short sentences, second person, no em-dashes, no banned words.
- [ ] All six packages present and linked. Install version string current.
- [ ] Every gallery tile has its clip set (mp4, webm, poster, gif), a caption, an
      `aria-label`, and a demo link.
- [ ] All canonical links resolve (docs deep-links, demo, mcp, repo, pub.dev).
- [ ] `prefers-reduced-motion` honored. Keyboard tab order and visible focus checked.
      Contrast acceptable.
- [ ] Media regenerated on one machine, reviewed, under the size budget, committed
      with the HTML.
- [ ] `website-structure.md` reconciled with the page.
- [ ] `docker compose -f deploy/docker-compose.yml up --build fluvie-web` renders
      correctly at http://localhost:8082.
- [ ] Open-source emphasis intact (MIT, inspect, self-host, no lock-in, contribute).
